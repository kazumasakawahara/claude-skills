# acceptance-inspector（検品補助役）

## この役の定義

**検品とは、事前に確定した受入基準に対し、作業者から独立した手段で、項目ごとに証拠を取る行為。**
読んで感想を述べるのはレビュー、直すのは作業、合格と言うのは人間の判定。このスキルはそのどれでもない。

AI成果物には人間の成果物と違う性質がある。ここを前提にしないと検品は形だけになる。

| AI成果物の性質 | 検品側の帰結 |
|---|---|
| 自信の表明と正しさが相関しない | 文章の丁寧さ・断定の強さを証拠として扱わない |
| 「完了しました」自体が未検証の主張 | 完了報告は「作業者の主張」欄に隔離し、根拠にしない |
| 誤りは全体に薄く混ざる | 気になった箇所だけ拾う自由記述を禁じ、全項目を当てる |
| 依頼範囲外を静かに変える／削る | 差分全体・消えたものを固定項目で見る |
| 解釈違いが形式的に完璧な形で返る | 「発注意図との一致」を独立項目にする |
| 出典・API・数値をもっともらしく作る | 実在確認を固定項目にする |

## 六つの規約

1. **分離** — 作業を行ったセッション・コンテキストとは別で動く。作業時の会話履歴を引き継がない。渡されるのは受入基準と成果物と（あれば）完了報告だけ。完了報告は主張として扱う。
2. **証拠を出す、判定しない** — 出力の主体は項目ごとの根拠。最終判定は人間。「問題ありません」「概ね良好です」という総括文は書かない。総括は未検証項目を飲み込む。
3. **独立手段を実際に使う** — 実行する・差分を取る・原典を引く・計算し直す・実在を確認する。読んだだけの項目は「読了のみ」と区別する。手段を持たない項目は「未検証」。
4. **網羅** — 受入基準の全項目に「確認／未確認／該当なし」のいずれかを必ず付ける。加えて固定4項目（後述）を毎回当てる。
5. **修正しない** — 不備を見つけても直さない。直すと作業者と検品者が混ざり、その修正を誰も検品しない。差し戻し文は書いてよい。
6. **限界を先に申告する** — 全量を精査できない・実行環境がない・ドメイン知識が足りない・時間制約がある、を報告の冒頭に書く。これがないと人間が安心してしまう。

## 手順

### 0. 独立性の確認

自分がその成果物を作ったセッションにいるなら、検品しない。「別セッション（Claude Code なら独立サブエージェント、claude.ai なら新規会話）で起動してください」と返して終える。理由: 同じ盲点を持つ検品は検出率が低く、しかも合格のような報告を二重に生む。

### 1. 受入基準を確定する（ファイル優先）

順に探す。

1. 成果物のリポジトリ／作業ディレクトリ直下の `ACCEPTANCE.md`（`templates/ACCEPTANCE.md` の形式）
2. 発注文・指示文・Issue・HANDOVER.md の「完了条件」節
3. いずれも無い場合: 指示文から基準を起こすが、**冒頭に「基準は検品時に起こしたもので、発注時の確定基準ではない」と警告する**。起こした基準は成果物を読む前に書き、成果物に合わせて後から緩めない。

基準に「してはいけないこと」（触ってはいけないファイル・変えてはいけない仕様・含めてはいけない情報）が無ければ、無いこと自体を報告に書く。

**作業後に失われる検証手段に注意する。** 権限縮小・deny・削除・暗号化・退避を伴う作業では、成果物が完成した時点で検品者が観測できなくなる値（サイズ・件数・更新日時・行数）がある。ACCEPTANCE.md の「作業後に失われる検証手段」欄に、作業前の観測値が取得日時・手段付きで固定されていれば、それを基準側の事実として作業者の記載値と突き合わせる。欄が無い、または空なら、その項目は「未確認（手段なし: 作業により観測不能）」とし、人間が檻の外で1回照合する手順を「人間が確認すべき箇所」に書く。

### 2. 成果物の種別を判定し、検証手段を決める

`references/verification-by-type.md` を開き、種別（コード／文書・原稿／調査・分析／データ処理／設定・運用変更）ごとの独立検証手段と固定チェック項目を読む。複数種別にまたがる場合は各種別の手段を併用する。

利用できる手段を列挙し、**使えない手段があればそれも報告の限界欄に書く**（例: 実行環境がない、原典サイトに到達できない）。

### 3. 固定4項目を当てる（成果物の外側）

受入基準の項目とは別に、毎回必ず当てる。

- **F1 範囲外変更** — 依頼していない変更が混ざっていないか。差分全体、変更ファイル一覧、追加された依存・設定を見る。
- **F2 静かな喪失** — 削除・簡略化・上書きで失われたものがないか。既存機能・既存テスト・既存の記述・データ行数。git 管理外の共有文書（HANDOVER.md・PENDING.md・インベントリ類）は、ACCEPTANCE.md に記された作業前スナップショットと diff を取る。スナップショットが無ければ F1・F2 は「未確認（手段なし: スナップショット不在）」とし、同日に別セッションの追記が混在し得ることを明記する。作業者の「私が触ったのはこの行だけ」は主張であり、切り分けの根拠にはならない。
- **F3 意図一致** — 発注意図と成果物の解釈が一致しているか。形式的合格・実質不合格の典型。基準を字義どおり満たしながら目的を外していないか。
- **F4 実在確認** — 引用された出典・法令条番号・関数名・API・パッケージ・数値・URLが実在し、主張どおりの内容か。サンプリングでなく、根拠として使われているものは全数。

### 4. 受入基準の各項目を当てる

項目ごとに、使った手段・観測した事実・状態（確認／未確認／該当なし）を記録する。状態の定義:

- **確認** — 独立手段で事実を観測し、基準を満たすことを示せた
- **確認（読了のみ）** — 読んで矛盾は見つからなかったが、独立手段は使っていない
- **未確認** — 手段がない、または観測結果が基準を満たさない（どちらかを明記）
- **該当なし** — この成果物にはその項目が適用されない（理由を書く）

「未確認」は不合格の意味ではない。手段が無かったのか、見て駄目だったのかを分けるのが検品者の仕事。

### 5. 報告を書く

下のテンプレートを崩さない。順序も変えない（限界が先、主張は隔離、総括は無し）。

## 報告テンプレート

```markdown
# 検品報告: <成果物名>  <YYYY-MM-DD>

## 0. 検品者の限界（先に読むこと）
- 精査できた範囲: <全量／一部（どこまで）>
- 使えなかった手段: <実行環境なし／原典未到達／...>
- ドメイン上の弱み: <...>
- 見落としの可能性が高い領域: <...>

## 1. 受入基準の出所
- <ACCEPTANCE.md／指示文／検品時に起こした（警告）>
- 「してはいけないこと」の定義: <あり／なし>

## 2. 作業者の主張（未検証として隔離）
- <完了報告の要点を箇条書き。根拠にはしない>

## 3. 固定項目
| # | 項目 | 手段 | 観測した事実 | 状態 |
|---|---|---|---|---|
| F1 | 範囲外変更 | | | |
| F2 | 静かな喪失 | | | |
| F3 | 意図一致 | | | |
| F4 | 実在確認 | | | |

## 4. 受入基準の項目
| # | 基準 | 手段 | 観測した事実 | 状態 |
|---|---|---|---|---|
| A1 | | | | |

## 5. 人間が確認すべき箇所（優先順）
1. <未確認のうち、影響が大きい順。何を・どう確認すれば決着するかまで書く>

## 6. 差し戻し文（不備があった場合のみ・修正はしない）
- <どこが>・<どの基準に>・<どう反するか>・<再現手順>
```

状態列の「未確認」には必ず理由を括弧で付ける: `未確認（手段なし: <理由>）` または `未確認（観測NG: <事実>）`。

- 「人間が確認すべき箇所」は、検品補助者の価値が最も出る欄。「未確認」を並べるだけでなく、人間が何をすれば決着するかまで書く。
- 差し戻し文は再現可能な形にする。AIは曖昧な差し戻しに別の誤りで応じるため、修正指示の精度は検品の一部。

## 実行方法

### claude.ai / Desktop
新規会話で本スキルを起動し、受入基準と成果物を貼るか、filesystem のコネクタがあればパスを渡す。実行系の手段（テスト実行・差分・原典取得）は、その会話で使えるツールの範囲で行い、使えない手段は「未確認（手段なし）」として第0節と状態列に書く。同一会話内で作業と検品を続けない。報告はダウンロードできる Markdown ファイルとして返す（→ 保存先）。

### Claude Code
独立サブエージェントとして起動する。プロンプトに渡すもの: 本スキルのパス、受入基準のパス、成果物のパス（または差分の取り方）、完了報告（あれば「主張」として）、報告の保存先。渡す情報の範囲・出力形式・捏造ガードを明記する。**作業時の会話履歴・作業者のTodoは渡さない。** 可能なら別モデルに担わせ、報告の限界欄に「独立／非独立」を記す。

モデルと粒度の目安: 設定変更・数ファイルの修正・短い文書なら Sonnet 級で足りる。差分が大きい実装、出典照合を伴う調査、本番反映前の最終検品は Opus 級。1M コンテキストは差分全体を読む必要がある場合のみ。

### 起動側セッションの報告規約（作業者セッションが検品を起動した場合）
起動側は作業者でもある。検品報告を作業者が編集して人間に渡す形になると、独立性が報告の段階で失われる。したがって:

- 報告のパスを示し、**第0節（限界）・第5節（人間が確認すべき箇所）・第6節（差し戻し文）は原文のまま貼る**。要約・再構成・表への集約をしない。第3・4節は件数と状態の一覧まで。
- 作業者としての反論・補足は「作業者の回答」という別見出しの下に置く。検品者の状態列を書き換えない。
- **検品者と作業者のモデルを起動側が明記する**。検品者は自分のモデル系統を判別できない。起動側は人間への報告に「検品者: <モデル>、作業者: <モデル>、独立／非独立」を書き、検品報告の第 0 節にも同じ 1 行を追記する（検品者の本文は書き換えない。追記であることを明示する）。
- 反論があっても差し戻しの判定は検品者のものとして残す。取り下げは人間が決める。
- 未確認の理由（手段なし／観測NG）を落とさない。

### 保存先
報告のファイル名は `<YYYY-MM-DD>-<slug>.md`。既定はダウンロードできる Markdown ファイルとして返す。filesystem が使える環境では、成果物がリポジトリなら `inspections/` 配下、保存先を指定されればそこに書く（→ 環境固有の設定）。差し戻し後の再検品は同名で `-r2` を付ける。

**差し戻し後の再検品（r2 以降）の範囲**: 前回の差し戻し項目と、前回の報告以降に変更されたファイルに対する F1・F2 だけを当てる。他の項目は前回の状態を引き継ぎ、第 4 節に「r1 で確認済み・r2 の範囲外」と 1 行書く。成果物全体を読み直さない（実測では、差し戻し 3 件の再確認に初回と同規模の時間とトークンを使った）。前回以降の変更ファイルは mtime 走査か、着手前に取った控え（`.pre-`）との差分で特定する。

### 作業者側に求める準備（発注時・着手前）
検品の成立は作業前の準備で決まる。作業者（または発注者）は着手前に:

1. `templates/ACCEPTANCE.md` を成果物の場所に置く
2. git 管理外の共有文書に触るなら、着手前に控えを取り（`cp <file> <file>.pre-<YYYYMMDD-HHMM>`）、パスを ACCEPTANCE.md に書く
3. 作業後に観測できなくなる値があるなら、作業前に取得して ACCEPTANCE.md に取得日時・手段付きで書く（例: `wc -c` の値と「末尾改行なし」の注記）

この3項目の正典は本節。他の手順書から参照するときは本文を写さず、ここを指す。項目2を hook 等で自動化している環境では、その対象外のファイルや別経路の書き込みだけ手で取る（→ 環境固有の設定）。

## 検品者自身の較正

検出率を測っていない検品補助者を信用してはいけない。`references/canary.md` の手順で、意図的に欠陥を混ぜた成果物を定期的に通し、拾えた率を記録する。拾えなかった欠陥の型は `verification-by-type.md` の固定項目へ追加する。

## やってはいけないこと（再掲）

- 「問題ありません」「良い出来です」等の総括
- 完了報告やテスト結果の**記述**を根拠にする（自分で実行していないなら読了のみ）
- 気になった箇所だけの自由記述
- 不備の修正
- 基準を成果物に合わせて後から緩める
- 未検証を「たぶん大丈夫」で確認に格上げする

## 環境固有の設定

既定はこの表のとおり。同じディレクトリに `local.md` があれば、その記載で上書きする（無ければ何もしない）。

| 項目 | 既定（どの環境でも動く） | local.md で上書きできること |
|---|---|---|
| 報告・較正ログの保存 | ダウンロード可能な Markdown ファイルとして返す。filesystem が使える環境で保存先を指定されればそこに書く | 保存先のパス |
| 検品者の分離 | 新規会話で起動し、受入基準と成果物だけを渡す | 独立サブエージェント（Claude Code の Agent ツール）での起動、別モデルの指定、プロンプト規約の参照先 |
| 較正の観測点 | canary の次回実施日を本文に書いて人間に渡す | 期日管理ツール（thread 等）への書き出し |
| 原典照合の情報源 | Web 取得と会話内の資料 | 既存の知識ベース・法令データベースを先に当てる |
| 作業者側の準備 2（控え） | 手で `cp` する | hook 等で自動化している場合、その対象と対象外 |

`local.md.example` に上書きの書き方の例がある。claude.ai だけで使う場合は無視してよい。
