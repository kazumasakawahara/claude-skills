# acceptance-inspector 使い方（人間向け手順書）

SKILL.md は Claude が読む規約。このファイルは**人間が読む手順書**。まず「最短の使い方」だけ読めば使える。その先は、検品の精度を上げたくなったときに読む。

## 最短の使い方（3分版）

Claude に何かを作らせて「できました」と返ってきたとき、それを鑑定してもらう手順。

1. 作業が終わった会話で、Claude の最後の返答（成果物と完了報告）をコピーする
2. **新しい会話**を開く（できればシークレットチャット。プロジェクトの中で作業していたなら、プロジェクトの外で）。次を貼って送る

```
検品してください。

依頼した内容:
<最初に頼んだ文をそのまま>

Claude が返してきたもの:
<コピーした成果物と完了報告>
```

3. 返ってきた報告の「**人間が確認すべき箇所**」を自分で確かめる。「**差し戻し文**」があれば、それを元の会話に貼って直させる

守ることは二つだけ。

- 作業した会話と**別の会話**で検品する（同じ会話で「検品して」と言うと断られる。それが正しい動作）
- 新しい会話には**依頼文と結果だけ**を貼る。「こういう経緯でこう直した」という説明は貼らない（貼ると検品者がその解釈を引き継いでしまう）

検品者は「合格」とは言わない。項目ごとに「確認できたこと」「確認できなかったこと」を並べるので、最後に決めるのは自分。「結局大丈夫？」と聞きたくなるが、聞くと総括文が出て未確認の項目が埋もれるので、「人間が確認すべき箇所」を一つずつ潰すほうが早い。

以下は、この使い方で物足りなくなったときのための説明。読まなくても使える。

---

## 基本の考え方

検品は、作業者と別の立場が、事前に決めた受入基準に、独立した手段で証拠を取る行為。claude.ai には「別のエージェント」が無いので、**分離は人間が担う**。分離の実体は三つだけ。

1. 作業した会話は閉じ、**新しい会話**で検品する
2. 新しい会話に渡すのは **受入基準・成果物・完了報告（主張扱い）** だけ。作業の経緯・意図・工夫の説明は渡さない
3. 検品者は不備を直さない。差し戻し文だけを作業会話に戻す

これを崩すと、同じ盲点を持つ検品が「合格に見える報告」を二重に生む。

## 精度を上げる手順（claude.ai / Claude Desktop）

最短版では「作業前の状態」が検品者に見えないので、余計な変更や消えたものは「未確認」になる。そこを埋めたいときの手順。

| 段 | 誰が | すること |
|---|---|---|
| 0 | 発注時 | `templates/ACCEPTANCE.md` を成果物の場所に置き、受入基準と「してはいけないこと」を書く。作業後に観測できなくなる値や git 管理外の共有文書があれば、作業前の値・控えを取って記録する（SKILL.md「作業者側に求める準備」） |
| 1 | 作業会話の末尾 | 下の **引渡し票プロンプト** を貼り、作業者に票だけを出させる |
| 2 | 人間 | 新しい会話を開く。可能ならシークレットチャット（記憶・過去チャット参照が切れる）。プロジェクト機能で作業していた場合はそのプロジェクトの外で開く |
| 3 | 新しい会話 | 下の **検品プロンプト** に引渡し票を添えて貼る。検品者は SKILL.md を読み、使えるツール（ファイル読み取り・コマンド実行・Web 取得）の範囲で証拠を取り、報告を書く |
| 4 | 人間 | 報告の **第0節（限界）・第5節（人間が確認すべき箇所）・第6節（差し戻し文）** を読む。第5節の確認を自分で行う |
| 5 | 人間 | 差し戻しがあれば **第6節だけ** を作業会話に貼る。検品者の推論や自分の解釈は添えない |
| 6 | 再検品 | 修正後、また新しい会話で検品プロンプトを貼る。範囲は「前回の差し戻し項目」と「前回以降に変わったファイルの F1・F2」だけと明記する（SKILL.md「差し戻し後の再検品」） |

Desktop でファイルアクセスやコマンド実行のコネクタが使えるなら、検品者が自分で差分・テスト・件数照合を実行できる。Web のみの場合は、検品者が「何を実行して出力を貼ってほしいか」を項目ごとに指定し、人間が実行して貼り戻す往復になる。どちらでも、**作業者にテスト結果を貼らせない**（人間が自分で実行する）。

## 引渡し票プロンプト（作業会話の末尾に貼る）

```
作業を終了します。次の形式で引渡し票だけを出してください。経緯・意図・工夫の説明は書かないでください。

# 引渡し票
- 成果物の場所: <パスまたは添付。リポジトリならブランチ名と比較元（例: main）も>
- 受入基準: <ACCEPTANCE.md のパス。無ければ「なし。指示文は以下」として発注文を原文で引用>
- 触ったファイルと行: <列挙>
- 作業前の控え（スナップショット）: <パス。取っていなければ「なし」>
- 作業後に観測できなくなった値: <値・作業前の観測値・手段・取得日時。無ければ「なし」>
- 完了報告（主張）: <あなたの完了報告を3〜6行で>
- 使用モデル: <自分のモデル名>
```

## 検品プロンプト（新しい会話に貼る）

```
あなたは検品補助役です。acceptance-inspector スキルの SKILL.md の手順と報告テンプレートに従ってください。種別を判定したら references/verification-by-type.md も読んでください。

前提:
- あなたは作業者ではありません。作業時の会話は一切ありません。過去の会話の検索や記憶の参照はしないでください。
- 下の引渡し票の「完了報告」は作業者の主張であり、根拠にはしません。
- 差分・テスト・件数照合・原典取得など実行系の手段は、この会話で使えるツールで自分で実行してください。使えない手段は「未確認（手段なし: 理由）」とします。私が代わりに実行すべきことがあれば、コマンドと見たい出力の範囲を項目ごとに指定してください。
- 不備を見つけても修正しないでください。
- 合否は言わず、項目ごとの証拠と未確認を並べてください。総括文は書かないでください。
- 報告はファイル名 <YYYY-MM-DD>-<slug>.md の Markdown で返し（保存先の指定があればそこに書く）、第0節・第5節・第6節をこの会話に原文のまま貼ってください。
- 報告の限界欄に、検品者のモデル名と「独立（別会話・履歴なし）」を明記してください。

検品するのは以下です。

[ここに引渡し票を貼る]
```

再検品のときは、末尾に次を足す。

```
これは再検品（r2）です。範囲は前回の差し戻し項目と、前回報告以降に変更されたファイルの F1・F2 だけです。前回の報告: <パスまたは添付>
```

## よくある崩れ方

- **経緯を添えてしまう**: 「〇〇の理由でこう直した」を検品者に渡すと、検品者がその解釈を前提にする。引渡し票だけに絞る
- **作業者に検品させる**: 同じ会話で「検品して」と言うと、SKILL.md の手順0で断られる。断られるのが正しい動作
- **総括を求める**: 「結局大丈夫？」と聞くと総括文が出て、未確認項目が飲み込まれる。第5節を自分で潰す
- **差し戻しを要約して戻す**: 作業者は曖昧な差し戻しに別の誤りで応じる。第6節を原文のまま貼る
- **再検品で全部読み直す**: 初回と同じ時間と費用がかかる。範囲を明記する

## Claude Code で使う場合

独立サブエージェントとして起動する。渡すもの・渡さないものは SKILL.md「実行方法 › Claude Code」のとおり。環境固有の設定（保存先・モデル・自動化）は `local.md`（`local.md.example` 参照）。
